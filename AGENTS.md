# Repository Guidelines

## Project Structure & Module Organization
- `skezmod.py`: production patcher for `MANAGPRE.EXE` (main entry point).
- `scripts/research/`: experimental and recovery tooling used during reverse-engineering investigations.
- `docs/releases/`: versioned release notes (for example `v0.1.0.md`).
- `docs/research/valderrama/`: handover notes and research artifacts.
- Root-level metadata: `README.md`, `CHANGELOG.md`, `LICENSE`, `.gitignore`.

Keep production behavior in `skezmod.py`; keep exploratory logic in `scripts/research/`.

## Build, Test, and Development Commands
- `./skezmod.py --dry-run`
Validates signatures and patch plan without modifying files. Run from a PM99 install directory containing `MANAGPRE.EXE` (or `managpre.exe`).
- `./skezmod.py --json-output /tmp/skezmod_report.json`
Applies patch and writes a machine-readable report.
- `./skezmod.py --dry-run --no-branding`
Validates patch flow while leaving title branding bytes unchanged.
- `python3 -m py_compile skezmod.py scripts/research/*.py`
Quick syntax check before opening a PR.

## Coding Style & Naming Conventions
- Language: Python 3, 4-space indentation, PEP 8 style.
- Use explicit type hints and `@dataclass` for structured records.
- Use `UPPER_SNAKE_CASE` for addresses/signatures/constants (for example `CAVE_NULL_GUARD_VA`).
- Use `snake_case` for functions and variables; keep helper names descriptive (`_build_patch_plan`, `_va_to_file_offset`).
- Document non-obvious binary offsets and patch intent with short, direct comments.

## Testing Guidelines
- No formal automated test framework is committed yet.
- Minimum validation for patch changes:
- `--dry-run` on an unmodified target binary.
- Apply patch once, then rerun `--dry-run` to confirm idempotent signatures.
- For research scripts, include reproducible commands and observed offsets/checksums in your PR description.

## Commit & Pull Request Guidelines
- Follow existing history style: concise imperative subjects, optional scope prefix.
- Example: `Valderrama fix-forward: auto-migrate bad wrapper without --force`.
- Keep commits focused to one logical change.
- PRs should include:
- What changed and why.
- Exact commands run (`--dry-run`, apply command, syntax checks).
- Risk/rollback notes (backup behavior, `MANAGPRE.original*.exe` handling).
- Updated docs when behavior or CLI flags change.

## Security & Configuration Tips
- Do not commit proprietary game binaries or extracted database files.
- Treat `--force` as an expert-only flag; use it only after manual byte-signature verification.
- Preserve backup executables generated by the staged patch flow to support rollback.
